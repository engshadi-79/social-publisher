# Social Auto-Publisher (Free Stack)

## Goal
Build a fully free, cloud-hosted system that automatically publishes scheduled posts
(Arabic text + designed image) to:
- Facebook Page
- Instagram (Business/Creator account linked to the Facebook Page)
- Threads
- LinkedIn (personal profile, via the free self-serve Share on LinkedIn product)
- Telegram channel

No paid services. No always-on server. Everything runs on GitHub Actions.

## Hard constraints
- Zero cost: no paid APIs, no paid hosting, no n8n cloud, no Zapier/Make.
- Runtime: GitHub Actions scheduled workflows only. The owner's PC is never required.
- Content generation does NOT call any paid LLM API at runtime. Posts are written ahead of
  time by Claude Code (inside the owner's subscription) into the content queue.
  Optional: a pluggable `generator` module that can use the Google Gemini API free tier,
  disabled by default.
- All UI text and post content is Arabic (RTL). Images must render Arabic correctly
  (proper shaping, RTL, no broken letters).
- Secrets live only in GitHub Actions Secrets. Never commit tokens. Never print them in logs.

## Stack
- Python 3.12
- Playwright (Chromium) to render HTML templates to PNG
- Jinja2 for templates
- PyYAML for the content queue
- requests / httpx for API calls
- GitHub Actions for scheduling
- GitHub Pages (gh-pages branch) to host rendered images at public HTTPS URLs
  (Instagram and Threads require a public `image_url`; they cannot take file uploads)
- Cloudflare Workers AI (free daily allocation, no credit card) for AI background images,
  model `@cf/black-forest-labs/flux-1-schnell`; fallback: Pollinations.ai

## Content-aware images (core feature)
Every image must visually represent the meaning of its post, not just display text.
Pipeline per post:
1. **Visual prompt**: when Claude Code writes a post into the queue, it also writes
   `image.visual_prompt` — a concise English scene description that expresses the post's
   idea (subject, setting, mood, lighting, style). Rules for the prompt:
   - Always end with: "no text, no letters, no words, no watermark".
   - Culturally appropriate for an Arab audience; avoid faces when not needed.
   - Match brand mood (calm, professional; navy/teal tones when it fits).
   - Leave clean negative space where the title will sit (state "empty space at top" or
     "at bottom" according to the template).
2. **Generate background**: `src/imagegen.py` calls Cloudflare Workers AI with the prompt,
   size matched to the template aspect ratio. On failure or quota exhaustion, fall back to
   Pollinations.ai. If both fail, fall back to a branded gradient background and notify
   the owner (never block publishing).
3. **Compose**: the HTML template uses the generated image as background, adds a dark or
   brand-colored overlay for legibility, then renders the Arabic title/body, logo and
   handle on top with Cairo. Arabic text is NEVER generated by the image model.
4. **Cache**: generate the background once, during preview, and commit it under
   `content/media/{post-id}-bg.png`, so the owner approves the exact image that will be
   published. The publish workflow only regenerates if the file is missing.
5. **Regenerate on request**: `python src/preview.py --regen <post-id> [--seed N]` creates a
   new variant; the owner can also edit `visual_prompt` and regenerate.

Queue fields added:
```yaml
  image:
    title: "..."
    body: "..."
    style: editorial   # carousel only: blueprint|editorial|terminal|poster|sticky|duo
    visual_prompt: "a tidy desk with an open planner, morning coffee, soft window light,
      calm navy and teal tones, minimal, empty space at top, no text, no letters,
      no words, no watermark"
    seed: 42            # optional, for reproducible results
```

Extra secrets: `CF_ACCOUNT_ID`, `CF_API_TOKEN` (token with Workers AI permission only).

## Accounts / targets
`content/accounts.yaml` lists every publishable account (Facebook pages, Instagram accounts, Threads, Telegram) with the NAMES of its secrets (never values). Each platform has default account(s). A queue post may set `targets: {facebook: [fb-<id>], instagram: [ig-<name>]}` to pick accounts; omitted = defaults. State keys: `platform` for the default account (legacy-compatible) else `platform:account-id`. Secrets are passed to the workflows as `NAME: ${{ secrets.NAME }}` env lines inserted under the `# ACCOUNT-SECRETS` marker in publish.yml and health.yml by `scripts/add_account.py` (do NOT use `toJSON(secrets)`: it makes runs `action_required`). Add accounts with `scripts/add_account.py`.

## Content queue format (`content/queue.yaml`)
```yaml
- id: 2026-10-20-001
  approved: true              # only approved posts are published
  publish_at: "2026-10-20 18:00"   # local time, timezone from config (Asia/Hebron)
  template: tip
  image:
    title: "عنوان المنشور"
    body: "نص قصير يظهر على الصورة"
  platforms:
    facebook: "النص الكامل لفيسبوك مع الهاشتاقات"
    instagram: "نص إنستغرام مع الهاشتاقات"
    threads: "نص ثريدز (500 حرف كحد أقصى)"
    linkedin: "نص لينكدإن (3000 حرف كحد أقصى)"
    telegram: "نص تيليجرام"
```
- A platform key that is missing means: skip that platform for this post.
- Validate the whole file on every run (schema, lengths, duplicate ids, valid template,
  Threads text ≤ 500 chars, Instagram caption ≤ 2200 chars). Fail loudly with clear errors.

## Publishing logic (`src/main.py`)
1. Load queue and state.
2. Select posts where `approved == true`, `publish_at <= now (Asia/Hebron)`, and at least
   one target platform is not yet `published` in state.
3. Render the image once per post; push to gh-pages; get public URL.
4. For each platform: publish, store `{status, platform_post_id, published_at, error}`.
5. Idempotent: never re-post a platform already marked `published`. Retry failed ones on
   the next run, up to 3 attempts, then mark `failed` and stop.
6. Commit `state.json` back to the repo (bot commit, `[skip ci]`).
7. Send one summary message to the owner's private Telegram chat.
8. Support `--dry-run` (render + validate, no publishing).

## Platform notes
- **Facebook Page**: `POST /{page-id}/photos` with `url` + `message`, using a long-lived
  Page Access Token (derived from a long-lived user token so it does not expire).
- **Instagram**: two steps. `POST /{ig-user-id}/media` (image_url, caption) → poll container
  status until FINISHED → `POST /{ig-user-id}/media_publish`. Uses the Page token.
- **Threads**: `POST graph.threads.net/v1.0/{user-id}/threads` (media_type=IMAGE, image_url,
  text) → wait for processing → `POST /{user-id}/threads_publish`. Long-lived token lasts
  60 days: `refresh-tokens.yml` refreshes it weekly via `th_refresh_token` and updates the
  GitHub Secret using `gh secret set` with a fine-grained PAT stored as `GH_PAT`.
- **LinkedIn**: the free self-serve **Share on LinkedIn** product (scope `w_member_social`,
  no partner review). Per image: `POST /v2/assets?action=registerUpload` → PUT the bytes to
  the returned `uploadUrl` → collect the asset URN; then `POST /v2/ugcPosts` with
  `shareMediaCategory: IMAGE` and every asset in `media[]` (max 9). The post id comes back in
  the `x-restli-id` response header, not the body. Deliberately NOT the newer `/rest/posts`:
  its `commentary` field requires backslash-escaping `#`, `(`, `)`, `_` and more, which would
  mangle our Arabic hashtags. Author is `LINKEDIN_AUTHOR_URN` — switch it to
  `urn:li:organization:<id>` to post to a company page (needs Community Management approval,
  no code change). Limits: 3000 chars, 9 images, 150 requests/day per member.
  Token lives 60 days and programmatic refresh is MDP-partners-only, so the owner must re-run
  `scripts/setup_linkedin.py` every two months; `health.py` warns from 14 days out.
- **Telegram**: Bot API `sendPhoto` to the channel (`@channel` or numeric id), caption up to
  1024 chars; if longer, send photo then text as a reply.
- Pin the Graph API version in one config constant.
- Respect rate limits; add small delays between platforms.

## Video posts (`reel` template)
There is NO free AI text-to-video API (every option is trial credits or paid), and the
zero-cost rule stands, so a reel is **motion design, not generated footage**: the brand's own
scene template animated over a real stock photo. The AI writes the script and picks the photo
query; it never generates the frames. Never describe it to the owner as AI-generated video.

- `image.scenes`: 3–8 scenes, each `{kicker, title (≤70 chars), body (≤150), seconds (1.5–8),
  photo_query}`. Short text is a hard requirement, not a style preference: a viewer reads a
  scene in ~3 seconds.
- `src/video.py` captures frames one by one by calling `window.seek(t)` in the page before each
  screenshot — the animation is computed in JS, never with CSS animations, so the same post
  always produces the identical video regardless of machine speed.
- Frames are JPEG, not PNG: PNG encoding measured 691 ms/frame versus 111 ms, six times slower.
  20 fps, H.264 + yuv420p + faststart — the one encoding all five platforms accept.
- The dashboard shows a poster frame (`render_poster`, ~2 s) instead of building the whole
  video (~90 s) for every preview.
- Publishing: Telegram `sendVideo` (file upload) · Facebook `/{page}/videos` with `file_url` ·
  Instagram `media_type=REELS` + `video_url` · Threads `media_type=VIDEO` ·
  LinkedIn `feedshare-video` recipe then `shareMediaCategory: VIDEO`.
  Instagram, Threads and Facebook need the public gh-pages URL, so the MP4 is uploaded there
  unchanged (no JPEG conversion).
- `publish.yml` installs ffmpeg if the runner lacks it.

**Daily morning reel** (exception to the above, at the owner's request): every day at 09:00, `image.style: morning`,
3 optimistic phrases over real footage (coffee, roses, sunrise, nature). `src/morning.py`: Pexels portrait videos, else Pixabay (highest resolution, center-cropped), when
`PEXELS_API_KEY` or `PIXABAY_API_KEY` is set (URL stored per scene as `video_url` at generation time), otherwise real photos with a slow
Ken Burns move. Text is rendered by Playwright as transparent layers and composited by ffmpeg (ffmpeg's drawtext does
not shape Arabic). Topic `morning-greetings` is excluded from the normal topic rotation.

## Rendering rules
- `<html dir="rtl" lang="ar">`, Cairo font loaded via local `@font-face`.
- Brand from `brand/brand.yaml` (defaults: navy + teal palette, Cairo font).
- Auto-shrink font size when text overflows; never cut text.
- Output PNG at exact template size, deviceScaleFactor 1.
- Logo + handle footer on every image.

## GitHub Actions
- `publish.yml`: `cron: "*/30 * * * *"` + `workflow_dispatch`. Install Playwright Chromium
  with caching. `permissions: contents: write`. Concurrency group to prevent overlapping runs.
- Prefer a public repository (unlimited free Actions minutes, and GitHub Pages works on
  the free plan). Secrets stay safe in a public repo.

## Weekly content workflow (done by Claude Code with the owner)
When the owner says "جهّز منشورات الأسبوع" (prepare this week's posts):
1. Read `content/topics.yaml`. Write posts ONLY about the topics listed there, each entry with
   `topic: <id>`. Never invent topics outside the list (the validator rejects them). If the list is
   empty, ask the owner for topics first. Ask for the number of posts if not given.
2. **Trending hashtags (research every time, never from memory).** Note: the dashboard's Generate button (src/generate.py) uses Google Trends RSS as trend context because Gemini search grounding is not free for new projects; when Claude Code writes posts, use WebSearch instead: use WebSearch to find the
   Arabic hashtags that are trending *now* and relevant to each post's topic (Instagram, Threads,
   Facebook, Telegram differ). Mix 2–3 current trending tags + 2–3 niche tags + the topic's
   `hashtags_fixed`. Only use tags that actually relate to the post; never bait with unrelated trends.
   Caveat to tell the owner: there is no official free trends API, so this is web research at
   preparation time and trends may shift before the post goes out.
3. Images (the owner wants REAL-looking photos, not AI-looking art):
   - For explainer/case-study content prefer the `carousel` template (image.slides: cover + one idea per slide + final engagement question; caption in first-person storytelling with ✦ bullets and a closing question).
     Pick `image.style` to suit the post, so consecutive carousels never look alike:
     `blueprint` (case study, technical breakdown) · `editorial` (essay, opinion, long idea) ·
     `terminal` (code, tools, developer content) · `poster` (announcement, short strong message) ·
     `sticky` (tips, friendly checklists) · `duo` (comparisons, ordered steps).
     Omitting `style` is allowed: the renderer derives one from the post id (stable, and spread across styles).
     The six photo styles need photos: give each slide its own `photo_query` (2–4 English words for
     what that slide is about) plus a post-level `image.photo_query` as the fallback. Without any
     query the renderer falls back to a flat style, so a carousel never ships with empty image boxes.
   - Otherwise prefer the `infographic` template (numbered key points in `image.points`, always on-topic) or `split` for real photos (stock photos are ~1000px wide, so full-bleed `photo` looks soft).
   - Set `image.photo_query`: 2–4 English keywords for a real stock photo (Pexels), e.g.
     "woman planning day notebook window". Also keep `image.visual_prompt` as the AI fallback.
   - Choose a different `seed` per post (it picks a different Pexels result).
4. Write new entries into `content/queue.yaml` with `approved: false`.
5. Run `python src/preview.py` and show the rendered images; the dashboard also shows them.
6. After the owner approves, set `approved: true`, commit, and push.

## Build order
1. Repo skeleton, requirements, config, queue schema + validator.
2. Brand + 4 templates + `render.py` + `preview.py` (verify Arabic rendering visually).
3. Telegram publisher + notify (easiest to test end-to-end first).
4. gh-pages hosting.
5. Facebook, Instagram, Threads publishers.
6. Workflows (publish, refresh tokens, preview).
7. Arabic `README.md`: step-by-step setup for Meta developer app, Facebook Page,
   Instagram Business link, Threads app, BotFather, and adding GitHub Secrets.
8. Dry-run test, then one real test post per platform.

## Definition of done
- A post added to the queue with `approved: true` appears on all four platforms within
  30 minutes of `publish_at`, with a correctly rendered Arabic image.
- Failures are reported to the owner on Telegram with the platform and error message.
- Running the workflow twice never double-posts.
